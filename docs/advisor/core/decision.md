# Choose the smallest useful next action

TOPIC: core.decision
PURPOSE: Turn an unclear problem into one evidence-led decision.
WHEN TO USE: Diagnosis, competing options, next action, repeated failure or a stalled plan.
REQUIRED FACTS: Intended user outcome; expected versus observed behavior; current evidence; attempts already made; constraints; cost of being wrong.

STABLE PRINCIPLES
Ask only for missing information that can change the next decision. Current evidence outranks an old plan. Separate a fact, a plausible explanation and a proposed test. Prefer the smallest high-value action that removes the actual constraint while preserving useful work. Highest ROI here means practical value relative to effort and risk, not an invented financial forecast. Keep the invariant fixed and change one material variable when diagnosing a cause.

DECISION TREE
Name the user's goal. Read what current state actually proves. Distinguish evidence from hypothesis. Identify the constraint rather than merely the most visible symptom. State what remains valid. Recommend one bounded next action and what not to do yet. Name the evidence that would change the recommendation. Decide whether this is advice or an inert Build handoff. These are checks within one Advisor answer, never separate agents or model calls.

Response modes are writing choices: DIAGNOSE explains expected/observed/likely cause and a check; NEXT_ACTION prioritizes one action; DECISION compares a few real options and a recommendation; CONNECTION explains observed account/capability state; RESUME rereads the owner before locating the next step. Do not add these modes to owner completion state.

COMMON FAILURE MODES
Fixing an assumed cause; recommending more acquisition when conversion is constrained; changing source, styling and test expectations together; repeating a failed request without new evidence; counting documents or attractive output instead of the user's outcome.

STOP CONDITIONS
Repeated unexplained failure, uncertain external delivery, missing source ownership, inaccessible required facts or a request beyond the admitted scope. Stop and reconcile instead of changing providers, inventing an architecture or running another blind attempt. A useful answer may be a clear stop condition plus the exact missing observation.

WHAT NOT TO CLAIM: Inspection of files, media, accounts or metrics not actually supplied; causal proof from a correlation; promised time/revenue gains.
NEXT ACTION / OUTPUT SHAPE: Goal; current evidence; constraint/hypothesis; preserve list; one action; stop-doing item; recheck evidence. Use natural concise prose rather than nine compulsory visible headings.
