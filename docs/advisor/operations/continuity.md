# Getting started and resuming

TOPIC: operations.continuity
PURPOSE: Find the first useful action or resume from fresh owner state.
WHEN TO USE: Setup, existing project, restart/reopen, “where did I leave off?” or local versus published status.
REQUIRED FACTS: Desired outcome; available input; selected product/project; current owner status/receipt; last discussion only as a navigation hint.

STABLE PRINCIPLES
Redwood has three standalone products. Build works with an idea or supported existing application repository. Present works with an app recording or web flow. Grow works with product information, a site, content or owned assets. Use the product matching the input and goal; finishing all three is not a prerequisite.

The launcher collects a name, desired outcome, optional audience and agent preference. Setup readiness describes whether the local product entry responds; it is not a completed project, trusted executable, successful render or published campaign. The product owner still governs its files and action prerequisites. Choose the existing Codex account when native advice is wanted; local help and manual handoff remain useful without a model response.

DECISION TREE
For first use, identify one concrete outcome and select the matching input/product. Check setup with the existing launcher control; follow local start instructions if needed. The launcher does not start product processes itself. Build can receive its intake context; Present/Grow context is reviewed/copied into their existing intake. Setup alone does not create their projects.

For resume, locate the selected project and reread current state. Compare old discussion with the new revision/receipt. If current, explain the proved scope and next unfinished action. If stale, inspect the change and preserve useful source before fresh verification/render/review. If unknown or a required product is offline, say which fact is missing and where to check it. Do not reconstruct state from remembered topic IDs.

The existing small checkpoint preserves conversation/project/runtime preference and bounded discussion topics. It does not store questions, answers, reasoning, secrets, raw traces or product truth. Legacy topic names normalize to the current cards. Restart/reopen requires fresh owner evidence; Build execution trust also resets and must not be inferred from continuity.

COMMON FAILURE MODES
Calling an old pass current, treating a navigation pointer as a backup, assuming an export is hosted/published, or rerunning an uncertain external operation. EXPORTED != PUBLISHED; a local calendar is not a scheduler.

STOP CONDITIONS: Wrong/missing project, conflicting revisions, uncertain effects or a request to recover destructively. Reconcile before mutation; Advisor may prepare a Build handoff but never executes recovery.
WHAT NOT TO CLAIM: Completion, account access or persistent user data from setup/checkpoint existence.
NEXT ACTION / OUTPUT SHAPE: Selected project and current scope; remembered topic distinguished from fact; one useful owner action; missing evidence.
SOURCE STATUS: Distribution guidance. Owner source paths are indexed in knowledge.mjs; internal maintenance provenance is not distributed or verified by the public suite.
